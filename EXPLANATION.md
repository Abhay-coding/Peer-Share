## 1. What are we building?

**PeerShare** is a Java desktop application where two users can share small files directly with each other over a local network.

Each user runs the same program. The program will:

1. remember other peers using a database;
2. show files inside a safe `shared_files` folder;
3. connect to another peer through its IP address and port;
4. show that peer's shared files;
5. download a selected file; and
6. save download history in SQLite.

The first stage does not yet share files. It prepares a safe and portable base for the later stages.

## 3. Stage 1: configuration and logging

### `config.properties`

```properties
server.port=5000
shared.directory=shared_files
downloads.directory=downloads
```

This file separates settings from Java code. If a user needs a different port, they change this file instead of editing and recompiling Java.

- A **port** is like a numbered door used by a program on a computer. Later, PeerShare will listen for file requests on port `5000`.
- Folder names are relative, meaning they are created inside the project directory. This makes the project work on Windows and macOS without changing paths.

### `src/main/java/com/peershare/config/AppConfig.java`

`AppConfig` reads the settings file and gives the rest of the program safe access to them.

Important methods:

| Method | What it does | Why we need it |
|---|---|---|
| `AppConfig.load(Path projectRoot)` | Reads `config.properties`, checks the port, and creates required folders. | One central place for all startup settings. |
| `serverPort()` | Returns the TCP server port. | Later used by `PeerServer`. |
| `sharedDirectory()` | Returns the safe sharing folder. | Prevents the app from offering all files on the computer. |
| `downloadDirectory()` | Returns the download folder. | Keeps received files organized. |
| `databasePath()` | Returns the future `peershare.db` path. | The SQLite database will be stored locally. |

The code uses `Path`, `Files`, and `normalize()` instead of writing paths such as `C:\\Users\\...` directly. This is a good portability practice. `normalize()` also helps reject a configuration that tries to escape the project directory using `..`.

### `src/main/java/com/peershare/util/AppLogger.java`

`AppLogger` creates a logger called `com.peershare`.

We use Java's built-in `java.util.logging` library because it records useful technical messages for developers without showing confusing details to normal users. `setUseParentHandlers(false)` prevents the same log message from being printed twice.

## 8. Stage 2: models and validation

### Why do we need models?

A **model** is a small Java object that represents one real thing in the project. Instead of passing many unrelated values around the program, we group related information into one clear object.

### `src/main/java/com/peershare/model/Peer.java`

```java
public record Peer(long id, String name, String ipAddress, int port) { }
```

`Peer` represents a saved remote user. For example, Rahul's peer information may be:

```text
id: 7
name: Rahul
ipAddress: 192.168.1.20
port: 5000
```

We used a Java **record** because this class only stores data. Java automatically provides the constructor and methods such as `name()` and `port()`. A normal class would require extra boilerplate getters, constructor, `equals`, and `toString` code.

### `SharedFile.java`

`SharedFile` represents metadata about a file inside `shared_files`:

- `id`: database identifier;
- `fileName`: for example `notes.pdf`;
- `fileSize`: file size in bytes;
- `lastModified`: the last edit time.

We store metadata, not the actual file content, in Java objects and later in SQLite. The actual bytes remain in the `shared_files` folder.

### `DownloadHistory.java`

`DownloadHistory` represents one finished or failed download. It stores the filename, peer name, time, and a status such as `SUCCESS` or `FAILED`.

Later, the History tab will display these objects in a JavaFX `TableView`.

### `src/main/java/com/peershare/util/InputValidator.java`

This class protects the application before it tries a database or network operation.

| Method | What it checks | Why it matters |
|---|---|---|
| `validatePeer(...)` | Peer name and IP/host are not blank; port is valid. | Prevents a meaningless connection request. |
| `parsePort(...)` | Port is a number from 1 to 65535. | TCP ports have this legal range. |
| `isSafeFileName(...)` | File name has no `..`, `/`, or `\\`. | Prevents a peer from requesting a file outside `shared_files`. |

The unsafe-name check is an important security practice. A malicious request like `../secret.txt` means “go up one folder.” Our program rejects it before any file operation happens.

### Stage 2 tests

`ModelAndValidationTest.java` proves that the models hold the expected data and that validation:

- accepts a correct peer;
- rejects a blank name;
- rejects ports outside `1` to `65535`;
- rejects words instead of port numbers;
- accepts `notes.pdf`;
- rejects unsafe file paths.

## 9. Stage 3: SQLite schema and DAO CRUD

### Why do we need a local database?

In PeerShare, each user needs to store information across application restarts:
1. **Peers**: saved names, IP addresses, and ports of friends or classmates.
2. **Shared files**: the list of local files available to be shared.
3. **Download history**: a log of past downloads (which file was downloaded, from whom, when, and whether it succeeded or failed).

Instead of running a heavy database server like MySQL or Oracle, we use **SQLite**. SQLite stores the entire database inside a single local file (`peershare.db`). Each user has their own private database; databases are not shared over the network.

> **Important concept:** We store only **file metadata** (file name, file size in bytes, last modified timestamp) in SQLite. The actual file bytes remain in `shared_files` and `downloads`. Never store large file bytes in a relational database when the filesystem already does this efficiently.

### What is JDBC?

**JDBC (Java Database Connectivity)** is a standard API in Java (`java.sql.*`) that lets Java programs connect to relational databases. JDBC provides the interfaces:
- `Connection`: represents an open connection to the database.
- `Statement` and `PreparedStatement`: used to execute SQL queries.
- `ResultSet`: holds rows returned by a `SELECT` query.

Because JDBC is an abstraction, Java code stays identical whether connecting to SQLite, PostgreSQL, or MySQL. The **SQLite JDBC driver** (`sqlite-jdbc.jar`) supplies the engine-specific translation to read and write the SQLite file format via the connection string `jdbc:sqlite:<path>`.

### `src/main/java/com/peershare/db/DatabaseManager.java`

`DatabaseManager` manages the database lifecycle:
1. **File resolution**: holds the `Path` to `peershare.db` (supplied via `AppConfig` or directly in tests).
2. **Directory creation**: ensures the parent directory exists before attempting to connect.
3. **Connection factory**: provides `getConnection()` using `DriverManager.getConnection("jdbc:sqlite:" + databasePath)`.
4. **Schema initialization**: `initialize()` runs `CREATE TABLE IF NOT EXISTS` for all three required tables:

| Table | Columns | Purpose |
|---|---|---|
| `peer` | `id` (INTEGER PK AUTOINCREMENT), `name` (TEXT), `ip_address` (TEXT), `port` (INTEGER) | Stores saved peers for manual connection. |
| `shared_file` | `id` (INTEGER PK AUTOINCREMENT), `file_name` (TEXT), `file_size` (INTEGER), `last_modified` (TEXT) | Stores metadata of locally shared files. |
| `download_history` | `id` (INTEGER PK AUTOINCREMENT), `file_name` (TEXT), `peer_name` (TEXT), `downloaded_at` (TEXT), `status` (TEXT) | Tracks download outcomes (`SUCCESS` or `FAILED`). |

### What is the DAO (Data Access Object) Pattern?

The **DAO pattern** separates database access code from the rest of the application.
- UI classes and services should never write raw SQL.
- Instead, they call simple Java methods like `peerDao.findAll()` or `historyDao.create(...)`.
- If table names or SQL queries change in the future, only the DAO class needs an edit.

### `src/main/java/com/peershare/dao/PeerDao.java`

`PeerDao` provides full CRUD (Create, Read, Update, Delete) operations for peers:

| Method | SQL Operation | Description |
|---|---|---|
| `create(Peer peer)` | `INSERT INTO peer (...) VALUES (?, ?, ?)` | Saves a new peer and uses `Statement.RETURN_GENERATED_KEYS` to assign the auto-generated database ID. |
| `findAll()` | `SELECT id, name, ip_address, port FROM peer ORDER BY id ASC` | Returns all saved peers as a `List<Peer>`. |
| `update(Peer peer)` | `UPDATE peer SET name = ?, ip_address = ?, port = ? WHERE id = ?` | Updates an existing peer's details. |
| `deleteById(long id)` | `DELETE FROM peer WHERE id = ?` | Deletes a peer by ID. |

### `src/main/java/com/peershare/dao/SharedFileDao.java`

`SharedFileDao` tracks files available for sharing:
- `findAll()`: returns all shared file records.
- `replaceAll(List<SharedFile> files)`: completely synchronizes the table with the actual files in `shared_files`.
  - It wraps operations in a **database transaction** (`conn.setAutoCommit(false)`).
  - Deletes existing records (`DELETE FROM shared_file`).
  - Batch-inserts the new list using `stmt.addBatch()` and `stmt.executeBatch()`.
  - Commits the transaction (`conn.commit()`), or rolls back on error (`conn.rollback()`). This guarantees that a partial scan failure never corrupts the shared file list.

### `src/main/java/com/peershare/dao/DownloadHistoryDao.java`

`DownloadHistoryDao` logs every download attempt:
- `create(DownloadHistory entry)`: inserts a history record with the timestamp and status (`SUCCESS` or `FAILED`).
- `findAll()`: retrieves history entries ordered by ID.
- `deleteById(long id)`: allows users to remove entries from their history view.

### Date and time handling in SQLite

SQLite does not have an internal `DATETIME` data type. Instead, dates and times are stored as standard ISO-8601 text (for example, `"2026-10-18T12:15:00"`):
- When saving: `entry.downloadedAt().toString()` converts Java's `LocalDateTime` into an ISO string.
- When reading: `LocalDateTime.parse(rs.getString("downloaded_at"))` restores the exact `LocalDateTime` object.

### Security and best practices applied

1. **`PreparedStatement` for all SQL**: Values are passed through parameterized placeholders (`?`). This completely prevents **SQL Injection** attacks, even if a peer name contains quotes or SQL keywords.
2. **Try-with-resources**: Every `Connection`, `PreparedStatement`, and `ResultSet` is enclosed in a `try (...)` block. This guarantees that database handles and file locks are closed immediately, preventing resource leaks.
3. **No raw byte storage**: SQLite only holds lightweight metadata, preserving memory and query performance.

### Stage 3 tests

`DatabaseDaoTest.java` verifies all database and DAO operations using a temporary database file:

- Creates a `Peer`, verifies auto-assigned ID, updates it, reads it back, and deletes it.
- Replaces shared files in `SharedFileDao` and verifies atomic replacement.
- Creates a `DownloadHistory` entry, reads the status, and deletes it.

All tests run through `.\scripts\test.ps1` and pass cleanly.

### A short viva explanation for Stage 3

> “In Stage 3, I implemented persistent storage using SQLite and the DAO (Data Access Object) pattern. `DatabaseManager` creates and connects to `peershare.db` using JDBC and initializes tables for peers, shared file metadata, and download history. Each DAO isolates all SQL logic and maps table rows to immutable record models. ## 10. Stage 4: Shared-folder scanning and database synchronization

### What does this stage do?

In Stage 4, we connect the physical hard drive folder (`shared_files`) with our SQLite database:
1. It looks inside the `shared_files` directory on disk.
2. It detects all regular files placed there by the user.
3. It reads the metadata of each file: file name, byte size, and last modified date/time.
4. It passes this list to `SharedFileDao.replaceAll()` to automatically update the local database.

### Why do we need a separate `FileScanner` service?

In clean software architecture, different classes have clear, separate responsibilities:
- **UI classes** should only handle buttons, clicks, and tables.
- **DAO classes** should only execute SQL queries.
- **`FileScanner` (Service layer)** handles the file system operations and coordinates between the disk and the DAO.

This structure makes the project easy to understand, test, and explain in college evaluations.

### `src/main/java/com/peershare/service/FileScanner.java`

`FileScanner` uses modern Java NIO (`java.nio.file.*`) APIs for clean and fast file handling:

| Method | What it does | Why it matters |
|---|---|---|
| `FileScanner(Path sharedDirectory)` | Sets the directory to scan. | Allows scanning any folder (useful for isolated tests). |
| `FileScanner(AppConfig config)` | Convenient constructor taking application config. | Seamlessly hooks into our configured `shared_files` folder. |
| `scan()` | Reads direct files from the folder and returns `List<SharedFile>`. | Inspects actual files on disk without modifying the database. |
| `scanAndStore(SharedFileDao dao)` | Scans the folder and saves the result to SQLite. | One-step method called when the user refreshes shared files. |

### How `scan()` works step-by-step:

1. **Folder safety check**:
   ```java
   if (!Files.exists(sharedDirectory)) {
       Files.createDirectories(sharedDirectory);
       return List.of();
   }
   ```
   If the folder doesn't exist yet, it is automatically created and an empty list is returned instead of crashing.

2. **Reading directory contents**:
   `Files.list(sharedDirectory)` opens a stream of directory entries. We wrap it in a `try (...)` block (try-with-resources) so the operating system directory handle is always closed immediately.

3. **Filtering regular files only**:
   ```java
   if (Files.isRegularFile(entry))
   ```
   This is a crucial security and design rule:
   - Nested subdirectories are **ignored**.
   - Shortcuts, special device files, and hidden directories are **ignored**.
   - Only files placed directly inside `shared_files` are recognized.

4. **Extracting metadata**:
   - `entry.getFileName().toString()` gives the simple file name (e.g. `notes.pdf`).
   - `Files.size(entry)` gives the exact file size in bytes.
   - `Files.getLastModifiedTime(entry)` gives the OS modification timestamp, which we convert to standard `LocalDateTime`:
     ```java
     LocalDateTime.ofInstant(fileTime.toInstant(), ZoneId.systemDefault());
     ```

5. **Sorting the list**:
   `files.sort(Comparator.comparing(SharedFile::fileName));` sorts the list alphabetically by name, ensuring consistent display in JavaFX tables.

6. **Synchronizing with SQLite (`scanAndStore`)**:
   `scanAndStore` calls `scan()` and then passes the list to `SharedFileDao.replaceAll(scannedFiles)`.
   Because `replaceAll` executes inside an atomic database transaction:
   - If a file was added on disk, it appears in SQLite.
   - If a file was deleted on disk, it is removed from SQLite.
   - If a file was renamed, the old name is removed and the new name is added.

### Stage 4 tests

`FileScannerTest.java` verifies the scanner in two automated tests:

   - Creates a temporary folder containing two files and one subdirectory with an inner file.

2. `testScanAndStoreSynchronization`:

Run `.\scripts\test.ps1` to verify all tests pass.

## 11. Stage 5: TCP protocol, background server, and remote-list request

### Why TCP Sockets?

In peer-to-peer (P2P) systems, there is no central server like Google Drive or Dropbox storing everyone's files. Instead, **every peer acts as both a client and a server**:
- **As a server**: it listens for incoming connections from other peers and answers requests for its shared files.
- **As a client**: it connects to other peers to ask for their files and download them.

We use **TCP (Transmission Control Protocol)** sockets via Java's `java.net` package (`ServerSocket` and `Socket`):
- TCP is **connection-oriented** and **reliable**: data packets are guaranteed to arrive in the exact order they were sent without corruption or data loss.
- TCP provides a continuous stream of bytes between two programs over an IP network.

### PeerShare Application Protocol

Computers communicating over a socket need a common "language" or protocol. We created a lightweight, human-readable text protocol:

| Command / Response | Format | Meaning |
|---|---|---|
| `LIST` | `LIST\n` | Client asks the remote peer for its list of shared files. |
| `OK <count>` | `OK 2\n` | Server responds with the number of files available, followed by each file line: `<fileName>|<fileSize>|<lastModified>\n`. |
| `DOWNLOAD <name>` | `DOWNLOAD notes.pdf\n` | Client requests to download a specific file. |
| `OK <byteCount>` | `OK 2048\n` | Server announces the file exists and is 2048 bytes, immediately followed by the raw binary stream. |
| `ERROR <message>` | `ERROR File not found\n` | Server informs the client that the request could not be fulfilled. |

### `src/main/java/com/peershare/network/Protocol.java`

`Protocol` stores standard command constants and provides two crucial helper methods for reading and writing lines over network streams:
1. `writeLine(OutputStream out, String line)`: encodes the string to UTF-8 bytes, appends `\n`, and calls `out.flush()` so data is sent across the network immediately.
2. `readLine(InputStream in)`: reads byte-by-byte until a newline character (`\n`) is reached.
   > **Why byte-by-byte instead of `BufferedReader`?**
   > Standard `BufferedReader.readLine()` reads large chunks (e.g., 8192 bytes) ahead of time into an internal memory buffer. If a client sends a text header followed immediately by binary file bytes, `BufferedReader` would swallow some of the file bytes! Our `Protocol.readLine` stops reading *precisely* at `\n`, leaving subsequent binary file bytes untouched on the stream.

### `src/main/java/com/peershare/network/PeerServer.java`

`PeerServer` is the background listening engine:
- It creates a `ServerSocket` on the configured port (e.g. `5000`).
- It runs an **accept loop** on a dedicated background thread:
  ```java
  Socket clientSocket = serverSocket.accept();
  ```
  `accept()` blocks (waits) until a remote peer connects.
- For every incoming connection, `PeerServer` launches a new `ClientHandler` thread. This means multiple classmates can list or download files at the same time without blocking each other.
- All threads are marked as **daemon threads** (`setDaemon(true)`), ensuring the Java program can shut down immediately when the user closes the window.
- `server.stop()` safely closes the `ServerSocket`, ending the accept loop.

### `src/main/java/com/peershare/network/ClientHandler.java`

`ClientHandler` implements `Runnable` and executes on its own thread:
1. Reads the incoming request line using `Protocol.readLine(in)`.
2. If `LIST`:
   - It calls `fileScanner.scan()`. Scanning at request time ensures remote peers always see files currently in the folder, even if a file was added seconds ago.
   - Sends `OK <fileCount>`.
   - Sends each file's details separated by `|` (`fileName|fileSize|lastModified`).
3. If `DOWNLOAD <filename>`:
   - Checks if the filename is safe with `InputValidator.isSafeFileName`.
   - Checks that the file exists and is a regular file.
   - Sends `OK <fileSize>` followed by raw file bytes.
4. If unknown or invalid: sends `ERROR ...`.
5. Closes the socket automatically when the interaction completes.

### `src/main/java/com/peershare/network/FileTransferClient.java`

`FileTransferClient` handles client-side connections:
- `listRemoteFiles(Peer peer)`:
  - Opens a `Socket` to `peer.ipAddress()` and `peer.port()`.
  - Configures an explicit **connect timeout (3 seconds)** and **read timeout (5 seconds)** using `socket.connect(address, timeout)` and `socket.setSoTimeout(...)`. This prevents the application from freezing forever if a classmate turns off their computer or disconnects from Wi-Fi.
  - Sends `LIST\n`.
  - Parses the `OK <count>` response and populates a `List<SharedFile>`.
  - Closes the socket immediately upon completion (short-lived connection model).

### Stage 5 tests

`NetworkTransferTest.java` performs end-to-end network tests without requiring a second computer:

   - Puts two sample files into a temporary shared folder.
   - Uses `FileTransferClient` to connect to `127.0.0.1` (localhost) on the dynamic port and calls `listRemoteFiles`.
   - Verifies that both files, their sizes, and timestamps are returned accurately.
   - Calls `server.stop()` to cleanly release the port.
2. `testUnavailablePeerConnectFailure`:

## 12. Stage 6: File download, atomic cleanup, and history recording

### What does this stage do?

Stage 6 completes the core file transfer engine:
1. A peer requests a file from a remote peer using `DOWNLOAD <filename>`.
2. The remote peer validates the request, sends the file size, and streams the raw bytes over the TCP socket.
3. The client receives the stream and writes it into a temporary `.part` file in `downloads/`.
4. Once the exact number of bytes is received and verified, the file is **atomically moved** to its final filename.
5. If an interruption, timeout, or security violation occurs, the incomplete `.part` file is immediately deleted.
6. Regardless of success or failure, a record is permanently logged in the SQLite `download_history` table.

### Why use temporary `.part` files?

In network applications, transfers can fail at any time due to Wi-Fi drops, sudden shutdowns, or timeouts.
- **Without `.part` files**: a user could end up with half of an image or a broken PDF inside their `downloads` folder without knowing it was incomplete.
- **With `.part` files**: the file is saved as `lecture_notes.pdf.part` during transit. If the transfer fails midway, the `.part` file is deleted. The real `lecture_notes.pdf` only appears in `downloads/` when it is 100% complete and verified.

### What is an Atomic Move?

In Java NIO, `Files.move(..., StandardCopyOption.ATOMIC_MOVE)` asks the operating system to perform the file rename as an atomic (indivisible) action.
- There is no point in time where the destination file is partially written.
- Other applications or user file explorers will never observe half-written files.
- If the filesystem does not support atomic moves (for example across different disk partitions), we gracefully fall back to `StandardCopyOption.REPLACE_EXISTING`.

### `src/main/java/com/peershare/service/TransferService.java`

`TransferService` is the high-level coordinator for file downloads:

| Method / Responsibility | Description |
|---|---|
| `download(Peer peer, String fileName)` | Full workflow: validates input, triggers download, moves file, and records history. |
| Security Check | Rejects path traversal attempts (e.g. `../secret.txt`) with an `IllegalArgumentException` before opening any network or file connection. |
| Cleanup on Failure | `catch` block guarantees `Files.deleteIfExists(tempFile)` is called if an exception occurs. |
| History Recording | Saves a `SUCCESS` row on completion, or a `FAILED` row if an error is caught. |

### How streaming works in `FileTransferClient.download`

```java
byte[] buffer = new byte[8192]; // 8 KB chunks
long totalRead = 0;
try (OutputStream fileOut = Files.newOutputStream(temporaryTarget)) {
    while (totalRead < expectedSize) {
        int toRead = (int) Math.min(buffer.length, expectedSize - totalRead);
        int bytesRead = in.read(buffer, 0, toRead);
        if (bytesRead == -1) {
            throw new IOException("Stream ended prematurely.");
        }
        fileOut.write(buffer, 0, bytesRead);
        totalRead += bytesRead;
    }
}
```
Key points:
- Reads in standard 8 KB chunks so memory usage stays tiny even for multi-megabyte files.
- Checks `totalRead < expectedSize` to avoid reading past the end of the file.
- If the remote peer disconnects early (`bytesRead == -1`), it throws an `IOException` and cleans up the partial file.

## 13. Stage 7: JavaFX desktop user interface and background tasks

### Why JavaFX?

JavaFX is Java's official modern toolkit for building rich desktop applications. It provides ready-to-use graphical controls such as:
- `TabPane` and `Tab`: organizes the application into clean, accessible tabs.
- `TableView` and `TableColumn`: displays structured data with sortable columns.
- `TextField`, `Button`, and `ComboBox`: handles user input and interactive actions.
- `Alert`: displays user-friendly popups for warnings, errors, and success confirmations.

### The Golden Rule of GUI Programming: Background Worker Tasks

> **Critical Concept:** In JavaFX, the **Application Thread** (UI thread) is responsible for rendering the window, drawing buttons, and handling mouse clicks. 
> 
> If you make a network connection (`socket.connect`) or download a large file on the JavaFX Application Thread, **the entire interface freezes**:
> - The window title shows "(Not Responding)".
> - Mouse clicks stop working.
> - Buttons cannot be pressed.
> 
> To prevent this, PeerShare runs all network operations inside background worker threads using `javafx.concurrent.Task`:
> ```java
> Task<Path> downloadTask = new Task<>() {
>     @Override
>     protected Path call() throws Exception {
>         // This runs in the background, keeping the window smooth
>         return transferService.download(peer, fileName);
>     }
> };
> downloadTask.setOnSucceeded(e -> {
>     // This automatically runs back on the UI thread when complete!
>     statusLabel.setText("Download complete!");
> });
> new Thread(downloadTask).start();
> ```

### Top 10 Viva Questions & Model Answers

1. **Q: Why is PeerShare a P2P architecture instead of Client-Server?**
   * **A:** In traditional client-server, all files are uploaded to a central server. In PeerShare, each peer runs both a `PeerServer` (server) and a `FileTransferClient` (client), allowing peers to transfer files directly to each other without any central intermediary.

2. **Q: Why did you choose SQLite over MySQL or PostgreSQL?**
   * **A:** SQLite is serverless and embedded. It stores the database in a single local file (`peershare.db`) and requires no background service installation, making PeerShare fully self-contained and portable.

3. **Q: Why don't you store file bytes directly inside SQLite?**
   * **A:** Storing large binary files (BLOBs) in a database bloats database size and hurts query performance. Operating systems and filesystems are already optimized for file storage. We store file metadata in SQLite and file bytes in `shared_files/` and `downloads/`.

4. **Q: How do you prevent Path Traversal attacks (e.g. `../secret.txt`)?**
   * **A:** `InputValidator.isSafeFileName()` rejects any filename containing `/`, `\`, or `..`. Furthermore, both `ClientHandler` and `TransferService` resolve and normalize paths, verifying that the target path strictly starts with the authorized base directory.

5. **Q: Why do you download to a `.part` file first?**
   * **A:** Network transfers can be interrupted by timeouts or Wi-Fi drops. Downloading to a `.part` file ensures incomplete or corrupted files are never presented to the user. Once the exact byte count is verified, `Files.move(..., ATOMIC_MOVE)` renames it in a single atomic step.

6. **Q: What is the DAO (Data Access Object) pattern?**
   * **A:** DAO separates the business and UI logic from database operations. Classes like `PeerDao` contain all SQL queries (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), allowing the rest of the application to deal only with Java objects.

7. **Q: How do you prevent SQL Injection?**
   * **A:** We strictly use `PreparedStatement` with parameterized placeholders (`?`) for all dynamic values. User input is never concatenated directly into SQL strings.

8. **Q: Why do you need `javafx.concurrent.Task`?**
   * **A:** JavaFX uses a single thread for UI rendering. Running long-running operations like socket connections or file downloads on the UI thread causes the window to freeze. `Task` runs the operation on a background worker thread and delivers results back to the UI thread safely.

9. **Q: What happens if a remote peer goes offline while we try to connect?**
   * **A:** `FileTransferClient` configures an explicit connect timeout (3 seconds) and read timeout (5 seconds). If the peer is unreachable, a controlled `IOException` is caught, a `FAILED` record is logged in SQLite, and a clear JavaFX error alert is shown to the user.

10. **Q: How did you implement cross-platform portability?**
    * **A:** We used Java NIO `Path` with relative paths instead of hard-coded Windows (`C:\...`) or Unix (`/...`) paths, configured paths through `config.properties`, and provided automated PowerShell (`.ps1`) and Bash (`.sh`) scripts.
